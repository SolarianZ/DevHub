## 当前状态（截至 2026-03-28）

- 当前分支：`m6`。
- M0~M5 已完成，Hub、`.NET SDK`、`JS/TS SDK`、`Python SDK`、Host 黑盒测试、跨语言 conformance 与 CI 门禁均已具备可工作的基线。
- 当前仓库主干布局为：`host/src/` 承载 Host 生产代码与 .NET 白盒测试工程，`host/tests/` 承载 Python 黑盒/集成/conformance 资产，`sdks/` 下按语言拆分 SDK 工作区，`docs/` 下集中维护规范、指南、运维与版本化协议资料。
- M6 第一阶段已完成 `host/tests/` 分层收敛：`assets/` 承载共享夹具，`blackbox/` 承载 Python 黑盒测试与 runner，`conformance/` 承载向量 / adapter / runner / 自测，`tools/` 承载覆盖率配置与辅助脚本。
- M6 不再以“新增协议能力”为主要目标，而是围绕“整理、优化、完善”推进发布前收尾，重点治理仓库目录、模块边界、依赖关系、测试分层和文档归档。
- 项目尚未正式发布，M6 允许做必要的破坏性调整；但必须区分“协议核心契约”和“发布前可调整约束”：不得通过修改 Spec 掩盖核心协议问题，但若识别出不贴合核心目标的冻结承诺、兼容口径或发布策略约束，应先修正规范，再同步实现、测试与文档资产。
- M6 的默认工作方式是“先审查并形成目标结构，再成批调整，再以完整本地验证确认收敛”，避免在未统一边界的情况下持续小修小补。

## 0. M6 目标与验收边界

### 0.1 M6 必须实现

- [ ] 先完成 M6 前置治理校准，明确 `Spec` 中哪些约束属于“核心目标必需”，哪些属于“发布前可调整”，并把该判断标准固定为后续任务的前置决策规则。
- [ ] 完成对 `host/`、`sdks/`、测试工程和文档目录的系统性盘点，明确“当前布局是否合理”与“目标布局应是什么”。
- [ ] 对不合理的目录放置、工程归属、命名与分层进行调整，确保生产代码、白盒测试、黑盒测试、协议资料和用户文档边界清晰。
- [ ] 审查 Host 与三套 SDK 的架构设计，识别并修复职责混杂、依赖方向不清、重复抽象、过度耦合和难以扩展的问题。
- [ ] 审查并修正单元测试、集成测试与 conformance 资产对 `Spec.md` 的符合性，清理不必要依赖具体实现细节的测试。
- [ ] 完成文档体系整理，使“规范、架构、开发、接入、运维、测试治理”各自有稳定落点，并移除过期或重复的里程碑细化文档。

### 0.2 M6 重点边界

- 允许调整：
  - 仓库目录结构。
  - Host / SDK 内部模块边界。
  - 尚未正式发布的 SDK 公共 API。
  - 测试目录、夹具、适配器和验证入口。
  - 文档分类、命名和归档方式。
- 默认不调整：
  - `docs/Spec.md` 中直接定义协议字段、错误语义、状态机、安全边界和序列化契约的核心行为。
- 允许在 M6 内重审并修正：
  - `Spec` 的冻结状态表述。
  - 发现字段冻结、兼容承诺、conformance 门禁等主要服务发布策略的约束。
- 若为解决根因必须触及公开行为，必须先判断该约束属于“协议核心契约”还是“发布前可调整约束”；前者优先回到实现或测试修正，后者允许修正规范并同步相关资产。

### 0.3 非 M6 范围

- 新增大版本协议能力或 v2 设计。
- 为发布而新增非必要的平台特定特性。
- 仅为了“看起来统一”而强行合并语义不同的模块或测试。

## 1. 审查对象与原则

### 1.1 仓库布局审查原则

- 生产代码、白盒测试、黑盒测试、版本化协议资产、终端用户文档必须能通过目录一眼区分。
- 不同技术栈工作区应保持各自独立，但跨语言共同资产应有统一、稳定、易发现的落点。
- 测试目录应体现分层意图，避免“黑盒、白盒、夹具、脚本、工具”混放后职责模糊。
- 文档目录应按用途分层，而不是持续在根目录平铺新增文件。

### 1.2 架构审查原则

- 优先保证模块职责单一、依赖方向稳定、扩展点清晰。
- 优先修复抽象失衡和边界错误，而不是继续在现有问题结构上叠加补丁。
- Host、SDK 与测试夹具之间的共享逻辑应只在真正稳定且跨场景复用时才提炼。
- 允许做破坏性重构，但必须成体系地同步测试、文档和验证命令。

### 1.3 测试审查原则

- 黑盒测试必须从 `Spec.md` 与公开行为出发设计，不得依赖内部实现、临时日志、私有状态或调用顺序。
- 白盒测试只验证公开职责难以覆盖的内部规则、边界分支和回归风险，非必要不绑定具体实现细节。
- conformance 向量、三语言 adapter 与 runner 必须保持中立，不能因为某个 SDK 的实现便利而改变断言口径。
- 应删减“实现一改就大面积碎裂、但并未提高规范保障”的脆弱测试。

### 1.4 `Spec` 治理原则

- M6 期间，`Spec.md` 仍是实现、测试与文档收敛的唯一权威基线，但不再等同于“已经永久冻结的对外承诺”。
- 后续任务在评估一个约束时，先回答两个问题：
  - 它是否直接服务“本机 per-user 多工具编排闭环”？
  - 它是在定义公开协议能力，还是在提前固化发布策略/兼容承诺？
- 若答案偏向前者，应优先改实现、测试或架构；若答案偏向后者，则允许在未正式发布前修正规范，并同步更新 Schema、示例、SDK、测试与接入文档。
- 当前基线下的默认分类结果：
  - `Spec` 中直接定义传输、发现、鉴权、scope、方法语义、状态机、错误语义与安全边界的条款，视为“核心目标必需约束”。
  - `Spec` 中关于冻结状态、发现字段冻结、兼容承诺、conformance 门禁和版本化资产发布口径的条款，视为“发布前可调整约束”。
  - 示例组织、资产打包和仓库发布流程说明，默认不应被当作需要在 M6 固化的协议能力。

## 2. 当前基线与重点疑点

### 2.1 已确认的当前基线

- `host/src/` 当前同时包含 `DevHub.Core`、`DevHub.Host`、`DevHub.Tests`、`DevHub.Host.Tests` 与 `DevHub.slnx`。
- `host/tests/` 当前按 `assets/`、`blackbox/`、`conformance/`、`tools/` 四层收敛，分别承载共享夹具、黑盒测试、符合性资产与验证工具。
- `sdks/dotnet/` 已形成独立解决方案与 `src/` / `tests/` 分层；`sdks/javascript/` 与 `sdks/python/` 也已按语言工作区独立维护。
- `docs/` 当前集中放置规范、规划、指南、运维资料，并包含 `schema/`、`protocol-examples/`、`assets/` 等版本化资源目录。

### 2.2 M6 需要重点核查的疑点

- `host/src/` 内同时放置生产工程与测试工程，虽然符合部分 .NET 仓库习惯，但与当前 `host/tests/` 的黑盒体系、`sdks/*` 的布局风格并不完全一致，需要重新判断是否仍是最佳方案。
- `host/tests/` 目前既包含黑盒测试，也包含 conformance runner、adapter、覆盖率配置与脚本，后续规模继续增长时可能出现职责边界模糊、导航成本升高的问题。
- 三套 SDK 的目录形态已基本独立，但其内部抽象层级、扩展点暴露方式、单元测试粒度和集成测试夹具风格是否足够一致，仍需要系统性审查。
- 文档已累计多类资料，M6 需要确认“规范/规划/开发/接入/运维/测试治理/版本化资产”是否已有稳定分类，避免继续以新增根级文档的方式堆叠。
- M5 阶段留下的历史里程碑文档需要压缩与归档，避免多个文档并存但职责重叠、引用过期。

## 5. 本地验证基线

M6 期间凡涉及代码、目录、工程文件、测试资产或 CI 入口的改动，提交前至少应完成以下本地验证：

- `dotnet build host/src/DevHub.slnx -c Release`
- `dotnet test host/src/DevHub.slnx -c Release`
- `dotnet build sdks/dotnet/DevHub.DotNetSdk.slnx -c Release`
- `dotnet test sdks/dotnet/DevHub.DotNetSdk.slnx -c Release`
- `npm --prefix sdks/javascript ci`
- `npm --prefix sdks/javascript run build`
- `npm --prefix sdks/javascript test`
- `python -m pytest sdks/python/tests`
- `python -m unittest discover -s host/tests/conformance -p "test_conformance_runner.py"`
- `python host/tests/conformance/vector_runner.py`
- `python host/tests/blackbox/test_runner.py --fast --no-header`
- `python host/tests/blackbox/test_runner.py --full --no-header`
- `python host/tests/blackbox/test_runner.py --smoke --no-header`
- `python host/tests/tools/verify_coverage.py --root . --line-threshold 0.90 --branch-threshold 0.80`

补充约束：

- 若改动触及 `host/tests/` 结构、conformance runner 或 SDK adapter，还必须补跑对应的专项回归。
- 若改动只涉及文档，且不影响 CI、代码路径、测试入口或工程结构，可不执行上述代码验证。

## 6. 风险与控制措施

- 目录迁移可能导致解决方案、脚本、CI、文档和本地命令同时失效，因此必须成批调整并一次性回归。
- 允许破坏性调整并不等于允许“边改边漂移”；每次重构都必须先明确目标边界，再落实现。
- 测试治理阶段容易把“历史上能跑通”误当成“符合 Spec”，必须始终以 `Spec.md` 与公开契约为准重新审视断言。
- 若发现某处问题同时涉及目录、抽象和测试三层，应优先做成一组完整收敛，不要只修表层症状。

## 7. 假设与默认选择

- 默认项目当前阶段以“内部优先、先把闭环做稳”为主，不以外部生态冻结承诺为首要目标。
- 默认 M6 以“整理与收敛”为主，不主动扩充协议能力。
- 默认允许对未发布 SDK API、测试布局和文档结构做破坏性调整。
- 默认 `docs/Spec.md` 仍是唯一权威标准，任何实现与测试都必须向它对齐；但其中的发布策略与兼容冻结约束在正式发布前允许按核心目标修订。
- 默认 M6 结束时，仓库应进入“可发布前冻结”的状态，而不是继续保留明显的结构性债务。
